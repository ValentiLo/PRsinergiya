| Критерий | Waterfall | V-модель | Incremental | Iterative | Scrum |
|----------|-----------|----------|-------------|-----------|-------|
| **Структура** | Последовательные этапы | Каскад + тесты на каждом уровне | Проект разбит на части | Повторяющиеся циклы | Спринты 2–4 недели |

## 3. Задание 2. Сравнительный анализ

**Сравнение Waterfall, Agile (Scrum), DevOps:**

| Критерий | Waterfall | Agile (Scrum) | DevOps |
|----------|-----------|---------------|--------|
| **Гибкость** | Низкая | Высокая | Высокая |
| **Обратная связь** | В конце проекта | Каждый спринт (2–4 нед.) | Непрерывно |
| **Риски** | Обнаруживаются поздно | Обнаруживаются рано | Обрабатываются постоянно |
| **Документация** | Много (ТЗ, ГОСТ) | Минимум (User Stories) | Средне (инфраструктура как код) |
| **Стоимость изменений** | Высокая | Низкая | Низкая |
| **Размер команды** | Большая (10+) | Малая (5–9) | Средняя (5–15) |
| **Сроки** | Предсказуемы | Гибкие | Гибкие, непрерывные релизы |
| **Подходит для** | Госзаказ, банки | Стартапы, веб | Веб-сервисы, SaaS |

**Вывод:**  
- **Waterfall** — для проектов с **фиксированными** требованиями и жёсткими сроками.
- **Agile (Scrum)** — для проектов с **меняющимися** требованиями и активным заказчиком.
- **DevOps** — для **непрерывной** доставки и эксплуатации.

## 4. Задание 3. Выбор методологии для кейса

### Кейс А. Государственный заказ

**Описание:** разработка системы учёта для министерства, требования зафиксированы в ТЗ, сроки жёсткие, бюджет фиксирован, заказчик не готов к изменениям.

**Выбранная методология:** **Waterfall (каскадная)**.

**Обоснование:**
- Требования **зафиксированы** — изменения не планируются.
- Бюджет и сроки **жёсткие** — нужна предсказуемость.
- Документация должна быть **полной** по ГОСТ.
- Заказчик **не готов** к итерациям.

**Риски:** позднее тестирование.  
**Как обрабатываются:** чёткое ТЗ + промежуточные проверки на каждом этапе.

---

### Кейс Б. Стартап

**Описание:** мобильное приложение для доставки еды, требования меняются, нужно быстро выпустить MVP, заказчик активно участвует, команда 5 человек.

**Выбранная методология:** **Agile (Scrum)**.

**Обоснование:**
- Требования **меняются** — нужна гибкость.
- Нужно **быстро выпустить MVP** — спринты по 2 недели.
- Заказчик **активно участвует** — Product Owner в команде.
- Команда **маленькая** — Scrum подходит идеально.

**Риски:** «расползание» требований.  
**Как обрабатываются:** Product Backlog с приоритетами, Sprint Review.

---

### Кейс В. Банковская система

**Описание:** модернизация внутренней системы банка, высокие требования к безопасности, долгий срок эксплуатации, регулярные обновления, команда 20 человек.

**Выбранная методология:** **гибридная — Waterfall + DevOps**.

**Обоснование:**
- **Безопасность** — фиксированные требования (Waterfall для планирования).
- **Регулярные обновления** — DevOps для CI/CD.
- **Команда 20 человек** — разделение на подкоманды.
- **Долгий срок** — нужна документация.

**Риски:** устаревание технологий.  
**Как обрабатываются:** регулярные ретроспективы, обновление стека.

## 5. Задание 4. Сравнение Agile-фреймворков

**Заполненная таблица:**

| Критерий | Scrum | Kanban | XP |
|----------|-------|--------|-----|
| **Итерации** | Спринты (2–4 нед.) | Непрерывный поток | 1–2 нед. |
| **Роли** | PO, SM, Team | Нет строгих | Coach, Team |
| **Планирование** | Sprint Planning | По мере необходимости | Planning Game |
| **Изменения** | Между спринтами | В любой момент | Приветствуются |
| **Документация** | Минимальная | Минимальная | Минимальная |
| **Практики** | Daily, Review, Retro | WIP-лимиты | TDD, Pair Programming |
| **Подходит для** | Продуктовых команд | Поддержки, ops | Критичных проектов |

**Вывод:**
- **Scrum** — для **продуктовых** команд с чёткими спринтами.
- **Kanban** — для **поддержки** и **непрерывного потока** задач.
- **XP** — для **критичных** проектов с высокими требованиями к качеству.

## 6. Задание 5. Анализ реального проекта

**Проект:** Telegram.

**Определение методологии:** **Agile (Scrum + Kanban)**.

**Обоснование:**
- Регулярные **обновления** — Agile.
- **Открытая** документация для API.
- Активное **участие пользователей** (бета-версии).
- **Быстрая** реакция на баги.

**Вывод:**  
Telegram использует **гибкие** методологии. Waterfall не подошёл бы — слишком медленный.

## 8. Задание 7. Эссе

**Тема:** «Сравнение методологий: плюсы и минусы»

**Пример эссе (кратко):**

> **Введение.** Методология проектирования определяет, как создаётся ПО. Выбор методологии влияет на сроки, бюджет и качество.
>
> **Waterfall.** Плюсы: предсказуемость, документация. Минусы: негибкость, позднее тестирование.
>
> **Agile (Scrum).** Плюсы: гибкость, обратная связь. Минусы: требует активного заказчика, сложно планировать.
>
> **Сравнение.** Waterfall подходит для госзаказа, Agile — для стартапов. DevOps — для веб-сервисов.
>
> **Вывод.** Нет универсальной методологии. Нужно выбирать под проект.
