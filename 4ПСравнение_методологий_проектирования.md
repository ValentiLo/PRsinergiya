## 2. Краткая теория

### 2.1. Что такое методология проектирования

**Методология проектирования** — это совокупность принципов, методов и практик, определяющих **как** создаётся программный продукт: как планируется работа, как распределяются роли, как обрабатываются изменения.

### 2.2. Основные методологии

| Методология | Суть |
|-------------|------|
| **Waterfall (каскадная)** | Последовательные этапы |
| **V-модель** | Каскад + тестирование на каждом уровне |
| **Incremental (инкрементная)** | Проект разбит на части |
| **Iterative (итеративная)** | Повторяющиеся циклы улучшения |
| **Spiral (спиральная)** | Витки + анализ рисков |
| **Agile (гибкая)** | Итерации, обратная связь, изменения приветствуются |
| **Scrum** | Agile-фреймворк: спринты, роли, артефакты |
| **Kanban** | Визуализация потока задач |
| **XP (Extreme Programming)** | Парное программирование, TDD, частая интеграция |
| **DevOps** | Объединение разработки и эксплуатации |
| **Lean** | Устранение потерь |

### 2.3. Критерии сравнения

| Критерий | Что означает |
|----------|--------------|
| **Гибкость** | Легко ли менять требования |
| **Обратная связь** | Как часто заказчик видит результат |
| **Риски** | Как обрабатываются |
| **Документация** | Сколько её |
| **Стоимость изменений** | Дорого ли вносить правки |
| **Размер команды** | Для кого подходит |
| **Сроки** | Предсказуемость |
| **Подходит для** | Каких проектов |

### Задание 3. Выбор методологии для кейса

**Условие:** даны 3 кейса. Для каждого выбрать методологию и обосновать.

**Кейс А. Государственный заказ**

> Разработать систему учёта для министерства. Требования зафиксированы в ТЗ. Сроки жёсткие. Бюджет фиксирован. Заказчик не готов к изменениям.

**Кейс Б. Стартап**

> Создать мобильное приложение для доставки еды. Требования меняются. Нужно быстро выпустить MVP. Заказчик активно участвует. Команда 5 человек.

**Кейс В. Банковская система**

> Модернизировать внутреннюю систему банка. Высокие требования к безопасности. Долгий срок эксплуатации. Регулярные обновления. Команда 20 человек.

**Что делать:**

1. Для каждого кейса выбрать методологию.
2. Обосновать выбор (3–5 предложений).
3. Указать, какие риски и как обрабатываются.

**Пример ответа для кейса А:**

> Для госзаказа подходит **Waterfall**. Требования зафиксированы, изменения не планируются, бюджет и сроки жёсткие. Документация должна быть полной по ГОСТ. Риск — позднее тестирование, но он компенсируется чётким ТЗ.

### Задание 4. Сравнение Agile-фреймворков

**Условие:** сравнить Scrum, Kanban, XP.

**Что делать:**

1. Заполнить таблицу:

| Критерий | Scrum | Kanban | XP |
|----------|-------|--------|-----|
| Итерации | Спринты (2–4 нед.) | Непрерывный поток | 1–2 нед. |
| Роли | PO, SM, Team | Нет строгих | Coach, Team |
| Планирование | Sprint Planning | По мере необходимости | Planning Game |
| Изменения | Между спринтами | В любой момент | Приветствуются |
| Документация | Минимальная | Минимальная | Минимальная |
| Практики | Daily, Review, Retro | WIP-лимиты | TDD, Pair Programming |
| Подходит для | Продуктовых команд | Поддержки, ops | Критичных проектов |

2. Сделать вывод: чем Scrum отличается от Kanban, а XP — от обоих.

### Задание 5. Анализ реального проекта

**Условие:** выбрать реальный проект и определить его методологию.

**Что делать:**

1. Выбрать проект (например, «Википедия», «Telegram», «Сбербанк-Онлайн»).
2. Определить, какая методология используется (по косвенным признакам):

   - открытость документации.
3. Обосновать.
4. Сделать вывод: подошла бы другая методология?
